# 中文回复里的七种问题

每条是一种机制，后面是真实回复里出现过的例子和该怎么写。判断时按机制判，例子帮你认出这种机制。

1. **英文动词直译。** 先有英文动词，再逐字换成中文。例：「抛出 RecursionError」（throw）、「跑完」（run）、「折回 spec」（fold back）、「还挂着等你定」（pending）、「问题还在」（still stands）、「13 条站住」（stand）、「由测试兜住」（catch）、「吐元素」（emit）、「它自己也说不推」（push）。该写：报错、运行完、写回、还没定、还没回答、成立、测试会报、取出、不 push。
2. **两字动词缩成一个字。** 「核对」缩成「核」、「接受」缩成「接」、「答得虚」缩成「答虚」。例：「我自己核过」「我没接的」「写完跑」。该写完整的词。只查动词；「但是」写成「但」、「文件名称」写成「文件名」这类连词和名词的简写不算。
3. **给新概念造中文名，或把该用英文的技术名词翻成中文。** 例：「烟雾测试」（smoke test）、「dashboard 两个面」（两个页面）、「两个洞」（两处错）、「停车球队」（占位球队）、「票 00」（ticket 00）、「提交进 git」（commit）、「退出码」（exit code）。该写标准英文名、用户已经用过的说法，或者一句大白话。
4. **用颜色或比喻代替结果。** 例：「是红是绿」（通过、失败）、「CI 绿了」（通过）、「守卫」（guard）、「魔法值」（sentinel value）、「没有牙」（不拦人）。该写字面意思。
5. **英文语序、英文介词，和把英文的检查条件直接当中文句子。** 例：「CI 结果目前不是 dev 的合并条件」（该写「现在 merge 进 dev 不看 CI 结果」）、「基于此」「在……的情况下」。写完成条件时，「bench/results/table.md 存在，退出码 0」是把 file exists、exit code 0 逐条搬过来，中文该先说做成了什么，文件和命令是证据：「Benchmark 的结果已经整理成 bench/results/table.md，每一格都填了数或 missing，`table` 命令能正常生成它」。该先写谁做什么、做成了什么。不必要的转折也算：「例子只是帮助认出来，不是词表」，「这不是 bug，而是设计如此」。判断办法是看有没有人真的说过被否定的那一半：没有人说过例子是词表，就不用先否定它，直接写它是什么。一条回复里这种转折出现不止一次，就按问题报。
6. **催答复、下命令的口气。** 例：「这份 sample 你接受吗」「你认不认」「认了我再……」「写吧。」「你必须选一个」。该写：「你觉得可以吗」「你看有要改的地方吗」，下一步用完整的句子说。
7. **同一个东西换着用不同的名字。** 一段话里同一个所指先后用了两个以上的名字，读的人以为在说几件事。例：同一段里「链 A」「主线」「agent 工程」说的是同一条线；「公开仓库」「public repo」「那个仓库」说的是同一个 repo。该写：一个概念全篇只用一个名字，用第一次出现的那个。第一次出现时解释它是什么（「链 A 是 agent 工程这条线」）不算换名字，不同的东西用不同的名字也不算。报这一种时，match 写换着用的几个名字，fix 只写该统一成哪一个名字。

不算问题的：技术名词和动词保留英文（deploy、merge、ticket）；没有现成中文说法的动词和名词也直接用英文，例如「把这条 open question close 掉」比「关门句」清楚；用户自己用过的词；引号里转述别人的原话；code 和链接。引号里的字如果是 agent 自己给东西起的名字或自己的说法，不算转述，照样按机制判，例如「正文里的『洞』全换成『一面答虚的两道题』」里引号内的「答虚」是 agent 自己造的。
